# 標本資料庫品質稽核框架
### Rule-based Data Quality Audit for a Biological Specimen Database

作者：董亭妤（國立中興大學生命科學系）

---

## 這個專案在做什麼

我在大學期間為國科會大專學生研究計畫自行設計並維護了一套蜘蛛標本資料庫，累積 154 筆標本紀錄，涵蓋 5 個屬、15 個分類單元、4 個國家、橫跨 2011–2025 年。

**這個專案的目標是將我過去基於生科研究建立的資料庫重新規劃為一套可重複、可擴充的資料品質稽核流程。**

我把資料庫當成一個需要被驗證的資料產品，設計了 10 條檢核規則，涵蓋值域檢查、類別編碼一致性、參照完整性、工作流程邏輯與缺失值分類，在原始資料中找出 31 筆品質問題，並依嚴重度逐項處理。

## 為什麼選用規則註冊表？

最直覺的做法是寫一連串 `if` 檢查。但這樣的程式碼一旦新增檢核項目就需要改動主流程，後續維護與更新容易有疏漏的風險，而且無法統一管理嚴重度與報告格式。

我改用裝飾器建立規則註冊表：

```python
@rule("GEO-01", "台灣樣本座標落在合理範圍外", "HIGH")
def check_coordinates(df):
    ...
    return violations_df
```

每條規則是獨立函式，回傳違規紀錄。主流程只走訪 `RULES` 清單，不需要知道有哪些規則存在，新增檢核只要寫一個新函式加上裝飾器。

## 檢核規則設計

規則分成五類，反映不同層次的資料品質問題。

### 一、值域與格式（Range & Format）

**`GEO-01` — 座標值域檢查**

台灣樣本的經緯度是否落在合理地理範圍內。找出 `ABARA_05994` 的經度記錄為 `102.829792`；該標本採集於屏東港口溪橋，緯度 22.05 正確，但經度應為 `120.829792`——`120` 與 `102` 的數字順序顛倒。

這個錯誤不會讓程式報錯，但等到將數據輸入進 QGIS 後就會發現該樣本出現在地圖上的寮國境內。

實作上有一個容易忽略的細節：`between()` 對 `NaN` 回傳 `False`，取反後所有缺座標的樣本都會被誤報成「座標錯誤」。規則中額外加上 `notna()` 條件，把「值有誤」與「值沒填」分開。

**`FMT-01` — 試算表自動轉換偵測**

原始紀錄中的 `8-16` 代表「8 日至 16 日」的採集期間，但試算表軟體會將其判讀為日期，改寫成 `08/16/2025`——連年份都是憑空生成的，原始資料中並不存在。

此與 Ziemann et al. (2016) 指出的問題同源：基因名稱 `SEPT2`、`MARCH1` 被 Excel 自動轉換為日期，污染了大量已發表研究的補充檔案，最終促使 HGNC 在 2020 年正式修改基因命名規則。

**修正時不需要改那三筆值，只需從源頭修正資料匯出流程即可**
將檔案從原始知識庫重新匯出，並在匯入試算表時將該欄位指定為文字格式。若只改值的話，下次匯出仍會被污染。

### 二、類別編碼一致性（Standardisation）

**`STD-01` — 分類層級一致性**

找出「Okinawa」與「Japan」並列為國別的問題。沖繩屬於日本的行政區，即使採集者的用意是標明差異，但兩者並列會讓任何以國別分組的統計失真。分類層級（granularity）不一致，因不屬拼字錯誤，一般的字串相似度比對抓不到。

**`STD-02` — 術語標準化**

找出 *Eriovixia excelsa* 同時被記為「艾瑟毛圓蛛」與「艾氏毛圓蛛」。與臨床資料中同一診斷有多種書寫方式的情況同構。

**`STD-03` — 字串哨兵值**

`"Missing"` 混入類別欄位，會被統計函式當成一個真實的類別。缺失應該以真正的空值表示。

### 三、參照完整性與業務規則（Referential Integrity）

**`REF-01` — 儲位規則**

檢查標本的實體儲位是否符合「一盒一屬」的設計慣例，找出 3 筆例外。

這條規則檢查的是**資料是否違反領域約定**——資料型別正確、值域正確、沒有缺失，但標本放錯了盒子。這類問題無法從資料本身看出來，必須把領域知識編碼成規則。

值得說明的是：**這 3 筆刻意未進行修正。** 這些標本可能是基於研究項目或空間考量刻意混放，也可能是規則本身需要修訂。正確的處理是回溯原始紀錄確認，進而釐清原因。

### 四、工作流程邏輯（Workflow Logic）

**`SEQ-01` — 流程跳階偵測**

定序流程的正常順序是「DNA 萃取 → COI 擴增 → 28S 擴增」。找出 6 筆 28S 已完成但 COI 無紀錄的標本。

這是本專案中技術上最有意思的一條規則：前面的規則都在檢查「單一欄位的值對不對」，這條規則的用意是檢查**欄位之間的邏輯關係是否符合時序**。

這 6 筆同樣列為待確認：可能是紀錄漏填，也可能是實際流程調整，後續處理會因原因不同而進一步調整。

**`SEQ-02` — 符號語彙一致性**

偵測到 `DNA` 與 `28S` 欄位使用 `●`，`COI` 欄位只使用 `◐`。

我編寫程式時的假設是：兩個符號表達同一個「已完成」語意，但在檢視結果後發現呈現出的效果和資料設計時的原定義並不相符，`◐` 在 `COI` 欄位中代表的是「已完成單向定序」，與 `●` 所屬的是不同的資訊，而非同一語意的兩種寫法。

因此這 3 筆資料所代表的是：**符號語彙缺乏明確的資料字典（data dictionary）**，使得外部讀者與分析程式都無從得知同一符號在不同欄位中的語意差異。後續應補上欄位層級的編碼定義，而非統一符號。


> 這是本專案中我認為最有價值的一次發現：**稽核規則本身也需要被稽核。** 

### 五、缺失值分類（Missingness）

**`MIS-01` — 結構性缺失 vs 隨機缺失**

`Chinese_name` 欄位有 66 筆缺失，看起來是嚴重的資料品質問題。但從結果來看：

- **結構性缺失**：未描述種（`sp.1`、`sp.2`、`cf.`）本來就還沒有中文俗名 → 不需要處理
- **隨機缺失**：同一學名的其他標本已有中文名，單筆缺漏 → 需要補齊，共 **1 筆**

從 66 筆問題變成 1 筆問題。

**「有多少缺失」是次要的，「哪些缺失需要處理」才是真正需要關注的問題。** 

### 補充：`GEO-02` 與規則的精度問題

**`GEO-02` — 同一地點名稱對應座標不一致**

檢查同一個 `Locality` 字串是否指向一致的座標，找出 2 個地點、5 組不同座標。

但進一步計算後發現，這些座標的實際差距是：中寮鄉南北相差約 7 公里、南澳鄉南北相差約 11 公里。鄉鎮層級本身就涵蓋十幾公里的範圍，在不同的具體地點採集卻只記錄到鄉鎮名。

這也暴露了規則實作上的一個問題：`nunique()` 使用浮點數精確相等比對。同一採集點的兩次 GPS 讀數若相差數公尺，也會被判定為不一致而誤報。合理的作法是引入容差，如將座標四捨五入至約百公尺解析度後再比對。

因此這條規則的定位從找出座標錯誤修正為**找出需要細化的地名記錄**。

## 資料保護：未描述分類群的地點去識別化

本資料庫的原始數據中包含數個尚未正式描述的分類群（`Bijoaraneus sp.1`、`sp.2`、`Aoaraneus sp.1` 等）。這些類群的模式產地在論文正式發表前不宜公開，部分稀有類群也有採集壓力的考量。

但直接刪除整筆紀錄會讓資料集失去分析價值。**去識別化的目標是把解析度降到足以保護、但仍可供分析的程度**。
處理腳本：`deidentify_localities.py`

### 處理內容

| 欄位 | 處理方式 | 效果 |
|---|---|---|
| `Latitude` / `Longitude` | 四捨五入至小數 2 位 | 約 1 公里解析度 |
| `Elve`（海拔） | 分組至最近的 100 公尺 | 降低山區的定位辨識度 |
| `Locality` | 一般化至縣市層級 | 移除可反查的精確地標 |

處理涵蓋 154 筆中的 67 筆紀錄，實測平均定位位移 0.49 公里、最大 0.56 公里。

### 為什麼必須同時處理地名，而不只是座標

原始資料中的部分地名精確到單一建物層級，例如「某某小吃」、「某某停車場」、「某某吊橋」。**任何人拿這些地名去查地圖，得到的精度都遠高於模糊化後的座標。**

只處理座標而保留精確地名，等於做了防護的形式卻沒有防護的效果。

這和醫療資料去識別化的原則也有相似之處：**準識別欄位（quasi-identifier）沒處理，主識別欄位處理了也沒用。** 這也是 HIPAA Safe Harbor 要求移除 18 類欄位、而不只是移除姓名的原因——生日、郵遞區號、就診日期單獨看都不是身分，組合起來卻足以重新識別個人。

### 無法自動處理的紀錄進入人工審查

腳本以縣市名稱樣式比對來一般化地名。**比對失敗的紀錄不會被靜默放行**，而是標記為 `LOCALITY_WITHHELD_PENDING_REVIEW` 並列入審查清單，由人工判定後補回規則。

初次執行時有 1 筆（`ABARA_05994`，地名僅記為「港口溪橋」，未含縣市）落入此清單，確認後補入規則表。

**去識別化管線不能有靜默失敗**——沒被規則涵蓋到的紀錄，如果預設放行，就會直接洩漏。這在臨床資料釋出流程中是同樣的要求。

### 一個非預期的發現：資料保護與品質規則會互相衝突

實施去識別化後重跑稽核，`GEO-02`（同一地點名稱對應座標不一致）的違規數從 6 筆暴增到 **23 筆**。

原因是：地名一般化後，「Yilan County, Taiwan」這個標籤底下自然會有許多不同的座標——**這也是去識別化的目的，但同時卻恰好觸發了檢查地名應對應一致座標的其他規則。**
即，**資料保護措施製造了資料品質規則的偽陽性。**

處理方式是在 `GEO-02` 中明確排除已一般化的地名，並在規則的說明文件中記錄這個互動：

```python
GENERALISED_LOCALITY_PATTERN = r"(?:County|City), (?:Taiwan|India|Philippines|Japan)$"
```

排除後違規數回到 5 筆（皆為未受保護類群的紀錄）。

> 這是本專案的第二個方法學發現：**資料治理的各項措施之間會互相干擾，不能各自獨立設計。** 在臨床資料場域，去識別化與資料品質查核由不同團隊負責是常態，這類衝突若未被明確處理，可能就會出現「查核系統一直報錯，但沒有人知道原因」的情形。

### 公開版與完整版的分離

本 repository 中的 `data/` 為**去識別化後的公開版**。完整解析度的資料保留於本機，不進入版本控制。

**重要附註**：稽核報告是在公開版資料上重新產生的，因此可由本 repository 的內容完整重現。實務上，資料品質查核通常在完整版上執行、釋出的則是去識別化版本，兩者不一定能相互重現——這個取捨需要在研究流程中明確界定。

## 這套方法在醫療資料上的對應

我做這個專案的動機，是把生物資料庫的管理經驗轉譯成健康資料科學的能力。以下列出兩者的問題結構相似之處：

| 本專案 | 醫療資料場域 |
|---|---|
| 標本儲位與工作流程追蹤 | 生物資料庫（Biobank）檢體管理、LIMS |
| 學名與中文俗名的標準化 | 診斷碼、藥品名稱的術語標準化 |
| 試算表自動轉換污染 | 基因名稱被 Excel 破壞（HGNC 2020 改名事件） |
| 定序流程跳階偵測 | 臨床試驗的收案流程稽核、edit check |
| 結構性 vs 隨機缺失 | EMR 缺失值機制判定（MCAR / MAR / MNAR） |
| 座標值域檢查 | 生理數值的合理範圍檢核 |
| 地名粒度與座標一致性 | 主資料管理（Master Data Management） |
